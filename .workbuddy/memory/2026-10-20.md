# 2026-10-20

## 缺点的解法设计（用户追问「能解决吗，怎么解决，要符合直觉」）
未落成文档，结论在对话内 + 一张「不是…而是…」映射图。

### 总则
**不发明新交互，借用人类已用几十年的心智物件**（编号、文件夹、视图切换、签字、撤销、快照）。
**能不解决的就不解决**——三个明确不做：多人协作、读屏无障碍、全局阅读顺序。

### 六条映射（错误方向 → 直觉解法 / 借用的模型）
1. 强加全局阅读顺序 → **只高亮当前关注链**（选中节点的上游来源 + 下游影响，其余淡出）= 地铁图高亮当前线路。承认空间无全局顺序，只在需要时给局部顺序。
2. 做版本管理系统 → **把集群收进抽屉**（框选一组节点→命名→折叠成卡片→归档区）。用「归档」这个所有人懂的动作表达「完成」，而不是引入版本概念。
3. 让 agent 自动判定形态 → **形态是用户可切换的视图**（同一节点多视图，一键降级为文本）。升级应是用户动作，不是系统判断；判定错了会困住用户，代价高于纯文本。
4. 做依赖可视化面板 → **hover 预览后果 + 可靠撤销**。人不关心依赖链，只关心后果（改数量看总价变化）；不敢动的真正原因是撤销不可靠，不是依赖不可见。
5. 让绑定容忍不确定性 → **确认即冻结，只绑 confirmed 节点**。复用已有的 draft/confirmed 两态：草稿可改，签署版不变；上游草案更新时不自动传播，只提示「是否同步」。
6. 让画布适合简单任务 → **双入口**（轻量问答不生成节点，可「提到画布」变成节点）= 相机自动/手动模式。不为了统一而统一。

### 最重要的一条洞察
**隐式依赖的解法不是「让它显式」（可视化），而是让它根本不存在**：
- 系统绝不自动推断依赖，绑定只能由用户亲手建立（自己连的线一定记得）
- 只绑已确认的节点（消除概率性）
- 影响预览 + 可靠撤销（消除不敢动）

## 画布本身是不是好形态（用户追问）
结论：**画布是好的出发点，但不是终点形态；它是探索态，不是交付态。**

- **核心论点：画布的适配度 ∝ 任务结构的不确定性**（见曲线图）。结构未知时画布 95 分，结构完全确定时降到 15 分；有序视图（文档流/分栏）反之。交叉点在「初步成型」。
- **最锋利的批评：x/y 是无语义的状态。** 用户用手工摆放隐式表达结构，用户累、系统一点学不到；自动布局则画布退化成 DAG 编辑器，自由价值消失。两难。
- **「全景可见」被高估**：可见 ≠ 可处理。人一次只关注一处，真正的价值是「需要时能快速调到」，而这搜索/聚焦也能给。
- **画布真正无可替代的只有两点**：不预设结构（唯一能容纳未知结构的形态）、并置比较（需要把两样东西放一起看时）。
- **推论（与上一轮方法论自洽）**：画布应降级为「一个视图」，与有序视图共享同一份数据。节点的形态是视图，场域的组织方式也是视图。
- **未验证**：原型从未测试过 >15 节点。可证伪的检验——30 节点时用户是缩放导航还是放弃；任务后能否凭记忆指出某节点位置；同一任务在文档流形态下的完成耗时对比。

## 更优雅的形态候选（用户追问「还有什么更好更优雅的形态」）
先定了「优雅」的标准：**用最少的机制覆盖最多需求，且不让用户手工维护结构**。

### 推荐答案：以大纲为骨架的活文档（见示意图）
- **顺序天然**（读的顺序 = 文档顺序）→ 解掉画布的阅读顺序问题
- **折叠即收口**：一次只展开一层，同时解决信息过载与「永不收口」
- **形态在块内**：块有类型（表格/清单/决策/文本），多态与顺序不冲突
- **依赖用引用表达，不用位置表达**（`依赖 → #4`）→ 引用是文本原生的：可跳转、可列表、可搜索，不需要摆放
- 附带全解：叙事回来了、可交付（导出成文档）、协作 / 无障碍 / 移动端全部天然成立
- 与 Wuji 立论不冲突：反对的是**聊天流**（按时间追加、不可重组的日志），不是文档（可编辑可重组的结构）

### 另外两个候选（点名但不选为场域形态）
- **电子表格**：依赖处理最优雅（地址 + 公式 + 自动重算），正好补上画布「位置无语义」的缺陷；但只适合做局部形态，承载不了叙事与长文本。
- **Notebook（Jupyter / Observable）**：过程可单独重跑，最贴合 Trace；但依赖自动推断恰恰是隐式依赖的来源，与已定的「绑定只由用户手动建立」冲突。

### 判断
**把「依赖」从空间位置移到引用，是从画布毕业的关键一步。**
最终方向：画布降为视图之一，默认视图为有序文档。与前两轮方法论完全一致——节点的形态是视图，场域的组织方式也是视图。

### 代价（诚实）
丢掉「一眼看到全景」的满足感、丢掉自由摆放；大纲对并置比较弱，需保留一个局部并排展开的口子。

## ★ 根源问题被用户重新定义（最重要的一轮）
用户指出前几轮都没碰到根源：**跟 Agent 对话时会有发散，但同时有主线**。
具体场景：Agent 回答了 A → 我对 A 有**疑问** → 也会有**发散**的对话 → **同时**还要让 A 继续往下执行主线。

### 真正的痛点（四个，聊天流与画布都没解决）
1. **阻塞**：有疑问就得先解决，主线被迫停下（共享一条流、一个输入框）。
2. **污染**：疑问/发散的内容混进主线上下文，主线继续跑时被带偏。
3. **关系丢失**：追问得到的答案（"为什么选涩谷"）与 A 没有结构关系——它本该修正 A 或成为 A 的脚注。
4. **回不来**：发散完如何回到主线，只能靠往上翻。

### 关键洞察：三种东西被平权了
主线（继续推进）· 疑问（针对 A 的质询）· 发散（从 A 长出去的新线）——现有形态全部压平。
- 聊天流：三者混在一条时间线里，主线被冲散。
- 画布：三者都是平权节点，画布没有"主干 vs 枝叶"的概念 → **画布把混乱从一维搬到了二维，没解决根源**。
- 前几轮讨论的「顺序/折叠/依赖」都没触及这一点（谈的是结构怎么摆，不是结构里的权重）。

### 解法：主线 + 两种旁支槽（见示意图）
- 每个节点挂两类旁支：**疑问 `?`**（质询该节点）与 **发散 `↗`**（从该节点长出去）
- **旁支独立上下文**：agent 只看到该节点 + 旁支历史 → 不污染主线
- **不阻塞**：主线继续跑，旁支悬着，节点上显示未解决计数
- **可并入**：疑问的答案→更新 A 的内容/置信度/来源；发散的成果→升级为主线节点或丢弃
- 虚线连接表示弱耦合

### 两个额外收获
- **疑问旁支 = 活的 trust cue**：不是展示一个置信度数字，而是让你真的去问，问完结果更新那个数字。直接兑现 Wavespace 第 2/3 条。
- **顺手缓解隐式依赖**：旁支上下文隔离，改动不外溢，除非显式「并入」——与已定的「绑定只由用户手动建立」同源。
- 与「活文档」完全兼容：**正文（主线）/ 脚注（疑问）/ 附录（发散）**。
